# MasterSeed SDK 需求文档

## 1. 文档信息

- 产品：Keymaster Seed SDK
- 仓库：MasterSeed
- 目标语言：Go、TypeScript
- 协议版本：Keymaster Seed V1
- 状态：已确认，可进入实现

本文定义产品范围、功能需求、非功能需求和验收标准。二进制格式和接口细节见[设计文档](./design.md)，实现任务见[施工单](./implementation-plan.md)。

## 2. 背景

Keymaster 需要用一个体积较小、可传播的种子文件描述一个源文件。SDK 将源文件按固定大小分块，计算每个数据块的 SHA-256，并将所有块摘要按原顺序拼接成种子文件。种子文件自身再计算一次 SHA-256，得到用于传播和内容寻址的 `seed_hash`。

Go SDK 与 TypeScript SDK 必须对任意相同输入产生逐字节完全相同的种子文件和 `seed_hash`。

## 3. 术语

| 术语 | 定义 |
|---|---|
| 源文件（source file） | 被分块和生成种子的原始数据文件 |
| 数据块（block） | 源文件中最多 512 KiB 的连续字节 |
| 块哈希（block hash） | 某个数据块的 SHA-256 原始摘要，固定 32 字节 |
| 种子文件（seed file） | 按块序依次拼接所有 32 字节块哈希得到的二进制文件 |
| 种子哈希（seed hash） | 对种子文件完整二进制内容计算 SHA-256 得到的摘要 |
| 块编号（block index） | 从 0 开始的数据块序号 |

## 4. 已冻结的 V1 决策

1. 块大小固定为 `512 KiB = 512 × 1024 = 524288` 字节，不是 512000 字节。
2. 哈希算法固定为 SHA-256。
3. 种子文件没有文件头、版本号或元数据，只包含块哈希序列。
4. 种子文件中的每个块哈希必须以 SHA-256 的 **32 字节原始二进制摘要**存储。
5. 种子文件严禁写入 64 字符的十六进制摘要文本。
6. `seed_hash` 在 SDK 内部以 32 字节摘要表达；对外传播和展示时使用连续的 64 字符小写十六进制。
7. 最后一个数据块可以小于 512 KiB；源文件恰好按块对齐时不得追加空块。
8. 空源文件合法，对应零字节种子文件。

## 5. 产品目标

- 为 Go 和 TypeScript 提供一致的种子生成、检查和校验能力。
- 支持流式处理大文件，不把整个源文件或种子文件加载到内存。
- 支持完整文件校验和独立数据块校验。
- 通过共享测试向量保证两个 SDK 的字节级兼容性。
- 为文件路径场景提供不会遗留有效名称半成品的安全写入接口。
- 提供结构化错误，便于 Keymaster 按错误类型处理。

## 6. 非目标

V1 不负责以下能力：

- 根据种子文件恢复源文件内容。
- 对源文件进行压缩、加密、纠删码或分发。
- 为发布者身份提供签名或认证。
- 在种子文件中保存文件名、源文件长度、媒体类型或时间戳。
- 支持可变块大小或 SHA-256 之外的算法。
- 定义 Keymaster 的网络传输协议、节点发现协议或持久化数据库结构。
- 提供命令行工具。

## 7. 功能需求

### FR-001 生成种子文件

SDK 必须能够流式读取源文件，每次最多将一个完整数据块交给 SHA-256 计算，并按块编号升序写出块摘要。

生成结果必须包含：

- 协议版本；
- 块大小；
- 块数量；
- 已读取的源文件字节数；
- 已写出的种子文件字节数；
- 32 字节 `seed_hash`；
- 规范化的小写十六进制 `seed_hash`。

### FR-002 计算和检查种子文件

SDK 必须能够：

- 对种子文件计算 `seed_hash`；
- 检查种子文件长度是否为 32 的整数倍；
- 根据合法长度计算块数量；
- 返回种子文件大小和 `seed_hash`。

仅计算出一个 hash 不代表文件结构合法；“计算 hash”和“严格检查”必须在接口语义上可区分。

### FR-003 验证种子哈希

SDK 必须能够将种子文件的实际 SHA-256 与调用方提供的预期 `seed_hash` 比较，并明确报告不匹配。

外部 hex 输入必须恰好表示 32 字节。输出始终使用小写；输入可以接受大小写字母，但不得接受 `0x` 前缀、空白或非十六进制字符。

### FR-004 验证完整源文件

SDK 必须根据种子文件逐块验证源文件，并区分：

- 某个数据块内容不匹配；
- 源文件提前结束；
- 源文件包含种子文件未描述的额外数据；
- 种子文件被截断或长度非法；
- 预期 `seed_hash` 不匹配；
- 底层读写失败或操作取消。

### FR-005 验证单个数据块

SDK 必须支持按块编号读取期望块哈希，并验证调用方提供的单个数据块。

- 非最后块必须恰好为 524288 字节。
- 在不知道源文件长度时，SDK 可以校验一个不足 524288 字节的数据块的摘要，但不能仅凭该块断定它确实是最后块。
- 越界块编号必须返回明确错误。

### FR-006 文件路径便利接口

除核心流式接口外，SDK 必须提供源文件路径和种子文件路径的便利接口。

生成路径接口必须先写同目录临时文件，全部成功后再发布到目标路径；失败时不得将不完整文件留在目标名称下。是否覆盖已有目标必须由显式选项控制，默认不覆盖。

### FR-007 操作取消

长时间生成和验证必须支持调用方取消。Go 使用上下文语义，TypeScript 使用取消信号语义。取消后返回可识别的取消错误，并停止后续读写。

### FR-008 跨语言兼容

Go 和 TypeScript 必须共享同一组黄金测试向量。对于每个合法输入，两者产生的以下结果必须完全一致：

- 种子文件的全部字节；
- 块数量和种子大小；
- `seed_hash` 原始字节；
- `seed_hash` 小写 hex。

## 8. 非功能需求

### NFR-001 确定性

输出只能由源文件字节决定，不得受文件名、路径、权限、修改时间、操作系统、输入流 chunk 边界或运行时影响。

### NFR-002 内存

默认顺序生成和验证的工作内存应保持在 `O(BLOCK_SIZE)`，不得随源文件大小增长。实现不得为了计算 `seed_hash` 而缓存完整种子文件。

### NFR-003 大文件安全

协议计数、文件大小和偏移必须按无符号 64 位语义处理。TypeScript 中不能用不安全的 `number` 表示可能超过 `Number.MAX_SAFE_INTEGER` 的文件偏移。

### NFR-004 错误稳定性

调用方必须能通过稳定的错误代码或错误类型判断失败原因，不能依赖自然语言消息解析。错误消息用于诊断，不构成兼容性协议。

### NFR-005 安全性

- 比较摘要时应使用适当的安全比较方法。
- 必须检查长度、偏移和乘法溢出。
- 从不可信输入读取时不得根据未验证值进行无限内存分配。
- 文档必须明确 `seed_hash` 是完整性标识，不是发布者签名。

### NFR-006 可测试性

核心逻辑必须可使用内存流测试，不依赖真实文件系统。路径封装另行进行集成测试。

### NFR-007 API 一致性

两个 SDK 的操作名称可以遵循各语言习惯，但能力、默认行为、边界条件和错误分类必须一致。

## 9. 验收标准

满足以下条件才视为 V1 完成：

1. 协议设计文档中的所有必测向量在 Go 和 TypeScript 中通过。
2. 对字符串 `abc` 生成的种子文件恰好为 32 字节，而不是 64 字节。
3. `abc` 的种子文件内容等于 SHA-256(`abc`) 的原始 32 字节摘要。
4. 对上述 32 字节种子内容再次计算 SHA-256，得到：
   `4f8b42c22dd3729b519ba6f68d2da7cc5b2d606d05daed5ad5128cc03e6c6358`。
5. 空源文件生成零字节种子文件，`seed_hash` 为 SHA-256 空输入摘要。
6. 对恰好 524288 字节的源文件只生成一个块哈希。
7. 对 524289 字节的源文件生成两个块哈希，种子文件恰好为 64 字节。
8. 修改任意源文件字节会导致对应块校验失败。
9. 修改、增加或删除任意种子文件字节会被严格检查或 `seed_hash` 校验发现。
10. 使用不同输入流 chunk 边界时输出保持完全相同。
11. 路径生成失败时，目标路径下不存在被误认为成功结果的半成品。
12. 两个 SDK 的公开 API、错误类型和使用说明完成文档化。

## 10. 发布约束

- V1 发布后，块大小、哈希算法和种子文件布局不得在原版本内改变。
- 任何影响种子文件字节的修改都必须定义新协议版本。
- 因为 V1 文件内部没有版本字段，Keymaster 应在协议上下文中明确其格式为 `keymaster-seed-v1`。
- 版本升级必须保留 V1 共享测试向量，防止兼容性回退。
